# hmi-incident-analyzer 使用说明书

> **智驾 HMI 事故工单批量结构化分析工具**
> 版本：1.0.0 | 适用对象：HMI 团队、安全分析团队、产品团队

---

## 一、工具是什么

`hmi-incident-analyzer` 是一个 Claude Code Skill，专为智驾 HMI 团队设计，用于**将飞书 Bitable 中的事故工单批量转化为结构化分析字段**。

一次调用可处理数百条记录，自动生成 6 个标准字段并直接写回飞书，替代人工逐条复制粘贴整理。

---

## 二、解决什么问题

### 现状痛点

| 问题 | 具体表现 |
|------|---------|
| 工单分散 | 事故描述、HMI方案、根因分析混在一个文本字段里，没有结构化 |
| 手动整理慢 | 每条工单需要人工拆分：事故场景/根因/系统方案/HMI方案 ≈ 5~10分钟/条 |
| 泊车记录空白 | 泊车碰撞工单无 HMI方案 字段，无法统计和分析 |
| 横向对比难 | 不同项目的事故无统一格式，无法批量统计高频场景或根因 |
| 关键词不标准 | 每人整理的关键词格式不一，检索和聚类困难 |

### 工具效果

- **500 条工单**：人工整理 ≈ 40~80 小时；工具处理 ≈ **15 分钟**
- **泊车空白记录**：从 0 到全部补全，生成标准化 HMI方案 + 6 字段
- **字段格式统一**：所有关键词按「功能类/场景类/根因类/告警类型/触发条件」标准分类

## 三、快速开始

### 前置条件

1. 已安装 Claude Code CLI
2. 已安装 feishu-sync（`pip install feishu-sync`）
3. 已完成飞书授权（`python -m feishu_sync.retoken init_token`）

### 最简调用

在 Claude Code 中输入：

```
/hmi-incident-analyzer
bitable: https://momenta.feishu.cn/wiki/XzJCw3mXIiYtWekt1Z2cqa1lnDh?table=tblUPCYZY1zQKlpu
```

Claude 会自动：
1. 读取 Bitable 所有记录
2. 识别行车/泊车碰撞记录
3. 分析并生成 6 个目标字段
4. 批量写回飞书

### 仅预览（不写入）

```
/hmi-incident-analyzer
bitable: https://momenta.feishu.cn/wiki/XXX?table=tblXXX
dry_run: true
```

## 四、参数详解

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `bitable` | URL | **必填** | 飞书 Bitable 地址（含 table= 参数） |
| `mode` | enum | `auto` | 处理模式（见下表） |
| `dry_run` | bool | `false` | 仅预览输出，不写入 Bitable |
| `limit` | int | `0`（全量） | 调试时限制处理条数，如 `limit: 10` |
| `scene_field` | string | `HMI-事故场景` | 自定义目标字段名 |
| `cause_field` | string | `HMI-事故原因` | 自定义目标字段名 |
| `text8_field` | string | `文本 8` | 自定义目标字段名 |
| `text9_field` | string | `文本 9` | 自定义目标字段名 |
| `text10_field` | string | `文本 10` | 自定义目标字段名 |
| `text11_field` | string | `文本 11` | 自定义目标字段名 |
| `hmi_field` | string | `HMI方案` | 源字段：HMI方案文本 |
| `func_field` | string | `功能分类` | 源字段：用于区分行车/泊车 |
| `driving_cats` | string | `行车碰撞,行车碰撞风险` | 行车碰撞的功能分类值 |
| `parking_cat` | string | `泊车碰撞` | 泊车碰撞的功能分类值 |

### 处理模式说明

| 模式 | 处理范围 |
|------|---------|
| `auto`（默认） | 行车碰撞（有HMI方案）+ 泊车碰撞（无HMI方案） |
| `driving` | 仅处理行车碰撞/行车碰撞风险记录 |
| `parking` | 仅处理泊车碰撞空白记录 |
| `all` | 对所有有 HMI方案 的记录重新生成（包括已填写的） |

## 五、生成字段说明

### HMI-事故场景

**内容**：「工单事件关键词 + HMI方案首句问题描述」

**示例**：
```
cut-in急刹车。AEB触发时HMI未给出接管提示，驾驶员未能及时响应导致追尾
```

**生成规则**：
- 从工单链接/标题中提取最后一段事件描述（`-` 或 `#` 后的内容）
- 拼接 HMI方案 的第一句话（含问题描述）
- 两者重复时只保留一个

---

### HMI-事故原因

**内容**：多维度根因组合

**示例**：
```
感知检出晚导致AEB触发延迟；感知漏检；制动力不足；故障漏报
```

**生成规则**（优先级从高到低）：

1. `备注`字段（人工填写的直接根因）
2. `二级分类`/`三级分类`（结构化根因标签）
3. `故障分类`（排除"非故障相关"）
4. HMI方案文本中含「原因/导致/异常/漏检/漏报」的句子

---

### 文本 8（ADAS 系统整体解决方案）

**内容**：基于故障分类的系统层解决方案模板 + 原始方案提炼 + 验证方式

**示例**：
```
【ADAS系统层面】①建立完整的感知/控制/传感器故障诊断上报链路，区分软硬件故障并分级上报；
②制定故障持续时间阈值，防止误报；原始方案：感知算法模型迭代，提升目标检出率；
【验证方式】通过场景注入测试验证降级触发时间<500ms
```

**故障分类 → 方案模板映射**：

| 故障分类 | 系统方案方向 |
|---------|------------|
| 故障诊断漏报/误报/延迟 | 完整故障诊断上报链路 + 冗余诊断通道 |
| 未打开降级 | 完善降级触发条件 + 多传感器联合失效覆盖 |
| 非故障相关 | 感知模型迭代 + 扩展设计包线 |
| 功能性能问题 | 性能优化 + 健康度自检 |
| 超出系统边界 | 安全裕度增加 + ODD 动态展示 |

---

### 文本 9（文本8 关键词分类）

**内容**：从文本8和HMI方案中提取的标准化关键词

**示例**：
```
功能类[AEB, FCW]；场景类[cut-in, 急刹]；根因类[感知漏检, failsafe未报]；方案类[故障诊断, 控制策略]
```

**关键词类别**：
- 功能类：HNP/UNP/AEB/FCW/LDW/LDP/APA/RPA/HPA 等 25 个功能名称
- 场景类：碰撞/追尾/变道/急刹/cut-in/行人/台阶/地锁 等
- 根因类：感知漏检/感知延迟/故障漏报/IMU零偏/制动力不足 等
- 方案类：故障诊断/感知模型迭代/系统降级/控制策略 等

---

### 文本 10（HMI 交互解决方案）

**内容**：从 HMI方案 中提取的交互层面内容

**示例**：
```
【HMI交互层面】①仪表盘红色闪烁告警并伴随语音播报"请立即接管"；
②系统降级时中控弹窗显示降级原因和接管引导；
③三联告警（视觉+语音+震动）在TTC<3s时触发，持续至驾驶员确认
```

---

### 文本 11（文本10 关键词分类）

**内容**：从文本10中提取的 HMI 交互关键词

**示例**：
```
功能类[AEB]；告警类型[视觉告警, 语音告警, 震动告警, 三联告警]；触发条件[TTC, 系统上限]
```

## 六、泊车碰撞知识库

对无 HMI方案 的泊车碰撞工单，根据工单关键词匹配以下知识库场景：

| 场景 | 匹配关键词 | 生成内容 |
|------|-----------|---------|
| 台阶/高差 | 台阶, 高差, 坡道 | APA泊入碰撞台阶，感知漏检，AVM标注高差区域 |
| 地锁/限位器 | 地锁, 限位, 地桩 | APA碰撞地锁，小目标弱势，停车场场景告警 |
| 路沿/路边石 | 路沿, 路边石, 揉库 | 揉库碰撞路沿，距离估算误差，方向性告警音 |
| 消防箱/悬空物 | 消防箱, 悬挂, 悬空 | 墙面悬挂物碰撞，高位盲区，人工确认提示 |
| 低矮柱子 | 柱子, 矮柱, 停车柱 | 立柱碰撞，底部盲区，AVM高亮显示 |
| 异形障碍物 | 障碍物, 异形, 购物车 | 非规则目标检出率低，占用栅格兜底 |
| 墙壁/角落 | 墙壁, 墙角, 死角 | 后方/侧方墙壁碰撞，距离精确显示 |
| 底盘/斜坡 | 底盘, 斜坡, 减速带 | 底盘刮擦，地面高程感知，坡度提示 |
| RPA 远程泊车 | RPA, 远程泊车 | 用户感知受限，三联告警，人工确认 |
| HPA 记忆泊车 | HPA, 记忆泊车 | 场景变化检测不足，场景差异告警 |
| 系统故障 | 故障, 传感器异常 | 传感器故障未提示，仪表弹窗告警 |

## 八、核心优势

### 1. 速度优势：节省 90%+ 整理时间

| 工作项 | 人工耗时 | 工具耗时 |
|--------|---------|---------|
| 阅读单条工单并填写 6 字段 | 5~10 分钟 | < 0.1 秒 |
| 500 条行车事故整理 | 40~80 小时 | ~8 分钟 |
| 200 条泊车记录从零补全 | 15~30 小时 | ~5 分钟 |
| **合计** | **55~110 小时** | **< 15 分钟** |

### 2. 质量优势：标准化输出，零遗漏

- **统一关键词分类体系**：所有记录采用同一套词表，后续可直接用关键词做频次统计
- **故障分类驱动的系统方案**：根据故障分类自动选择对应系统层改进方向，避免笼统通用描述
- **泊车知识库**：11 类停车场碰撞场景各有专属方案，覆盖行业主要弱势场景

### 3. 复用优势：团队共享，随时调用

- Skill 安装后全员可用，不需要每次重新写脚本
- 支持参数配置，适配不同项目的字段命名习惯
- 知识库可持续迭代，随着项目积累不断完善

### 4. 数据优势：支撑后续分析

字段结构化后，可直接在 Bitable 中：
- **按文本9关键词筛选**：找到所有「AEB + cut-in + 感知漏检」的事故
- **按文本11关键词统计**：哪类告警方案被使用最多
- **按场景类交叉分析**：行人场景 vs 车辆场景的 HMI 方案差异

## 九、工作原理

```
飞书 Bitable
    │
    ▼
读取所有记录（feishu-sync）
    │
    ├── 行车碰撞（有HMI方案）
    │       │
    │       ├── 解析工单事件 → HMI-事故场景
    │       ├── 多字段融合 → HMI-事故原因
    │       ├── 故障分类模板 + 原文提炼 → 文本8（ADAS系统方案）
    │       ├── 关键词提取 → 文本9
    │       ├── HMI句子抽取 → 文本10（HMI交互方案）
    │       └── 关键词提取 → 文本11
    │
    └── 泊车碰撞（无HMI方案）
            │
            ├── 工单关键词匹配知识库（11类场景）
            ├── 知识库生成 HMI方案（补全）
            └── 知识库生成全部 6 字段
    │
    ▼
批量 PUT 写回飞书 Bitable
（约 30 条/批，0.3s 间隔，避免限速）
```

## 十、常见问题

**Q: 飞书 token 过期怎么办？**
A: 运行 `python -m feishu_sync.retoken init_token`，在终端完成授权即可。

**Q: 某条记录写入失败（fail=1）怎么处理？**
A: 通常是瞬时网络中断，重新运行一次即可（工具是幂等的，重复运行不会产生重复数据）。

**Q: 我的 Bitable 字段名和默认不一样怎么办？**
A: 通过参数指定，如 `scene_field: 事故描述`，详见第四节参数表。

**Q: 支持非飞书数据源吗？**
A: 当前版本仅支持飞书 Bitable。数据可通过 `feishu-sync-cli download_file` 导出为 Excel 后离线处理，但写回功能需要飞书 API。

**Q: 泊车知识库不包含我们遇到的场景怎么办？**
A: 调用时通过 `extra_kb` 参数追加，或直接告知 Claude 新的场景描述，工具会在本次调用中临时扩充知识库。

**Q: 处理完后如何验证效果？**
A: 用 `dry_run: true` 预览前 10 条；或在飞书 Bitable 中按「文本 8 非空」筛选查看填写情况。
